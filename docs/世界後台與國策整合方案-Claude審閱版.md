# 世界後台與國策整合方案：Claude 審閱版

日期：2026-10-04  
狀態：設計草案，供審閱；尚未實作。本文不代表已授權修改程式。

## 1. 這次要解決什麼

世界後台與國策檔案各自呼叫模型更新，可能讀到不同時點的資料，或對同一段故事時間推演出不同結果。

希望工作流助手更新世界局勢時，同一次模型呼叫也處理國策，讓「國策行動 → 世界反應 → 後續國策選擇」在同一次推演中互相影響。

採用的分工是：**工作流助手保存世界結果並提供國策提案；國策檔案驗證、保存國策。失敗時可用國策檔案的手動「局勢更新」補救國策。**

## 2. 已釐清的邊界

- 世界資料由工作流助手管理；正式國策資料由國策檔案管理。
- 國策檔案的「局勢更新」只能修正國策，不能重跑或修正世界後台。
- 世界已保存、國策提案失敗，是本方案允許且需要處理的狀態。
- 不採用先前討論過的「兩邊驗證通過才共同保存」方案；本版不要求跨腳本共同提交、回滾世界或阻止世界刊報。
- 第一版整合局勢更新；辨識國家、生成國策樹、重大改樹及換期生成保留既有功能。
- 正常更新以同一次模型呼叫產生兩份結果；不承諾所有失敗情況都能自動修復或完全消除敘事矛盾。

## 3. 實際流程

```text
工作流助手準備更新世界
    ↓
取得本次世界資料＋國策資料＋共同目標時間
    ↓
模型同一次回覆：世界更新＋國策提案
    ↓
工作流助手照原流程保存世界結果
並將國策提案保存到獨立的接收欄位
    ↓
國策檔案確認對應世界更新已成功保存，讀取提案
    ↓
沿用國策規則驗證
    ├─ 成功：保存國策，記錄已處理
    └─ 失敗：保持國策原狀，記錄原因，允許手動局勢更新
```

接收欄位的路徑、結果通知方式及工作流助手的接入 API 均未定案，須先確認實際能力。提案不能在世界寫入失敗時被當成成功世界更新的配套結果套用。

## 5. 最小資料契約與時序要求

### 輸入

世界後台需要完整的國策判定資料，不能只讀提供給正文的迷霧摘要。優先重用現有 `taskData`、`workingState` 與 `ProposalSchema`，避免另維護一套資料格式。

國策資料必須在工作流助手組裝本次請求時可用。若採用預存欄位，要確認更新順序；不能假定國策自己的樓層完成事件一定比工作流助手更早發生。

### 提案附帶資訊

建議由程式記錄下列資訊，正式欄位名待審閱後決定：

- 請求識別，以及聊天、樓層與回覆分支識別。
- 本次涵蓋的世界／國家與目標故事時間。
- 提案依據的國策版本；世界來源版本或足以辨識該次更新的資訊。
- 對應世界更新是否成功保存。
- 原始國策提案及接收結果。

這些識別由程式產生和核對，不依賴模型自行聲稱「我是最新結果」。重送同一提案不能產生第二次效果。

### 時間與排程

世界上次刊報時間和各國 cursor 可以不同，但本次國策提案的終點須符合本樓來源故事時間；已處理區間不得重複結算。刊報日期只作時間參考，不能獨自證明本樓某項任務已完成。

世界後台未到排程時間時，整合模式下不另啟動自動國策推演。手動更新仍可補進度，但之後的世界請求必須讀取更新後的國策，不能重播舊國策區間。介面需讓使用者知道國策尚未追上本樓時間。

## 6. 失敗時如何補救

| 情況 | 處理 |
|---|---|
| 工作流助手整次失敗，世界未更新 | 由使用者在工作流助手重跑。國策檔案顯示尚無成功的對應世界更新。 |
| 世界成功，國策提案缺失、解析失敗或驗證失敗 | 顯示原因；使用者在國策檔案按「局勢更新」。 |
| 手動局勢更新 | 重新讀取最新世界結果與國策狀態，由國策自己的模型請求產生新提案，沿用原規則驗證，只保存國策。 |
| 世界結果無法合法對應國策 | 顯示具體衝突；不強制完成國策，也不由國策腳本回寫世界。 |
| 國策已保存，只是顯示尚未更新 | 重新讀取狀態，不再發放效果。 |

手動補救開始時，須使同一來源的待接收提案失效或暫停接收，避免它稍後與手動結果競爭。即使手動請求失敗，解除／恢復接收的規則也要明確，不能靜默套用已被取代的舊結果。

世界與國策雖分屬不同欄位，若底層都是整包樓層變量替換，仍可能互相覆蓋。要檢查工作流助手是否以最新資料合併保存，以及保存／通知的順序；分開欄位本身不保證避免覆寫。

## 9. Claude 審閱回覆（2026-10-04）

依第 7 節逐題查證，未修改任何程式。

**查證來源**

- 工作流助手原始碼：使用者酒館載入 `tavern_helper_template-main@v0.0.46/dist/工作流助手/index.js`（`settings.json` 內的匯入網址）。GitHub 已刪除該標籤，改用同日 bundle 提交 `1dc0d38`（2026-09-20）。下文行號皆指該提交。
- 實際任務設定：`F:\SillyTavern\data\default-user\settings.json` 中工作流助手的 `tasks`。世界任務「世界时局与经济简报」為 `structuredOutputMode: addon_json_patch`、`extractInjectTags: ["世界状态摘要@world", "UpdateVariable"]`，與 `docs/reference/workflow-assistant-preset-v6.3-命定之诗版.json` 一致。
- 實際執行紀錄：`chats/命定v4.2.1/chat___v4_2_1_20260813-110621.jsonl` 各樓的 `acu_workflow_run_status`。此檔最新刊報為 490-10-15（第 829 樓），不是使用者本次貼出的 10-20 那份；以下只用它確認執行路徑。

### Q1：結構化輸出能否攜帶額外提案

**純 JSON 路徑不能。**

- `extractStrictVariableResponse` 只取根物件的 `analysis` 與 `patch`，再以 `buildNormalizedVariableXml` 重組成 `<UpdateVariable>`；根物件其他欄位全部捨棄（`src/工作流助手/tasks/strict-variable-response.ts`）。
- 標籤抽取對重組後的文字執行（`tasks/runtime.ts:340`，`extractPlotTagsFromResponse(processedResponse || rawResponse, …)`），因此提案不會進入標籤。
- 改用 patch 寫入也不可行：`addon_data` 根 schema 只有 `世界`、`社交圈`、`位面交汇`（`src/addon-mvu/schema.ts:446`）。zod 物件預設剝除未知鍵，`normalizeAddonData` 會丟掉 `/国策提案`。

**XML 路徑可以。**

- 嚴格 JSON 解析失敗、但原文含完整 `<AddonJSONPatch>` 時，`resolveStructuredResponse` 直接採用原文（`hasCompleteVariableXml` 分支），其他標籤照常抽取。
- 第 829 樓即走此路徑：其執行紀錄抽到 `世界状态摘要@world=阿斯塔利亚` 與 `UpdateVariable`，前者不可能由純 JSON 路徑產生。
- 在 `extractInjectTags` 加入提案標籤（如 `国策提案`），結果會存入本樓 `post_process_tags` 與執行紀錄的 `extractedTags`。
- 使用者預設的 `finalInjectTemplate` 只含 `{{UpdateVariable}}`，提案不會被注入正文。

**可靠性問題**：結構化規則明寫「不要 XML」。模型若照規則輸出純 JSON，提案就會遺失。要穩定攜帶，只能二選一：

- (a) 世界任務改 `structuredOutputMode: off`，正式走 XML。只改預設；但原本為 DeepSeek 開啟結構化輸出，關閉後解析失敗率需實測。
- (b) 修改工作流助手原始碼，讓結構化模式保留並存取額外欄位（例如在 `extractStrictVariableResponse` 與 runtime 結果中帶出）。

**順帶發現（待使用者確認）**：同一機制下，`世界状态摘要` 也只在模型輸出 XML 時更新；模型照規則輸出純 JSON 時，摘要會停在舊版，而國策預設的世界局勢段正是讀這個摘要。這可能是局勢資料落後的另一個原因。

### Q2：能否辨識世界保存成功

**可以，不需新增完成標記。**

- 工作流助手沒有任務完成事件。`tasks/events.ts` 只發出 `acu-pp:tasks-changed` 與 `acu-pp:chat-scope-changed`。
- 每次執行後，`persistRunStatus`（`tasks/trigger.ts:351`）以 `writeRunStatusToMessage`（`tasks/run-status.ts:123`）把 `acu_workflow_run_status` 寫在該樓訊息物件頂層並存檔。內容含 `messageId`、`at`，以及各任務的 `taskName`、`success`、`skipped`、`extractedTags`。樓層快照會保留 `extractedTags`（`toFloorRunStatus`）。
- addon patch 在各階段結束即套用（`tasks/runtime.ts:639`，`applyVariableUpdatesAfterStage`），早於 `persistRunStatus`。因此讀到成功的執行紀錄時，世界資料已寫入。
- 另有公開 API：`window.parent.AcuPostProcessAPI.getRunStatusForFloor(messageId)`（`bridge/post-process-api.ts`）。
- 世界任務排程為依 `<tp>` 每週一次。該聊天檔多數樓層為 `skipped: true`，能區分「本樓未到期」「執行失敗」「成功」三種狀態。

**缺口**：執行紀錄掛在訊息頂層、不分 swipe（`run-status.ts:138`）。`at` 可作為該次執行的識別，但需與當前 swipe 的生成時間比對，才能確認屬於當前 swipe。只需改國策腳本：以既有計時器輪詢讀取。

### Q3：如何在請求開始前提供最新國策資料

**本樓開始前的國策狀態一定可讀。**

- 工作流助手等 MVU 的 `VARIABLE_UPDATE_ENDED` 後才派發任務（`tasks/mvu-trigger-defer.ts`），組提示詞時 EJS 讀本樓變量。
- 國策腳本在同一事件把上一樓的 `国策` 保留到新樓（本專案 `src/tavern.ts:280` 起）。

**時序無保證的是 `now` 與完整任務資料。**

- 這兩項目前由本專案 `src/workflow.ts` 的 `taskData` 在國策自己的任務中組裝。
- 國策腳本在 MVU 結束後靠 `setInterval` 計時器處理新樓（`src/tavern.ts`），與工作流助手的提示詞組裝誰先無保證。預存欄位可能讀到上一樓的資料。
- 本專案驗證要求 `proposal.until === snapshot.day` 精確相等（`src/workflow.ts:775`）。`179335.35416666663` 這類浮點值，模型很難照抄。

兩個解法：

- (a) **渲染當下現算（建議）**：國策腳本在 window 掛同步函式，世界任務的 EJS 在組提示詞時呼叫，即時算出本樓任務資料，不需預存，也沒有時序問題。需驗證 EJS 執行環境能存取該全域函式（模板在頁面環境執行，推測可行，未實測）。
- (b) **預存不含 `now` 的資料**：接收提案時由程式確認終點落在本樓故事日，再改寫成 `snapshot.day`。此法需放寬目前的精確比對。

**份量問題**：完整任務資料即國策局勢更新的整份輸入（各國整棵樹與 schema）。世界任務提示詞已約 7 萬字，合併後總量可能翻倍，token 與推演品質需實測。

### Q4：多世界副本如何分工

- 世界任務是副本族：`replicaFamilySpec: 世界状态摘要@world`，`replicaFamilyScheduleMode: manual`。每個降臨世界一個成員，例如執行紀錄中的「世界时局与经济简报 阿斯塔利亚」。每個成員渲染同一組提示詞段，國策段若無條件，每個世界都會提案全部國家。
- 國策 state 目前沒有「國家屬於哪個世界」的欄位。

最小做法分兩邊：

- **預設**：設定中指定一個世界負責國策；EJS 以預設已在使用的 `{{replica:val}}` 判斷，只對該世界送出國策段。
- **國策腳本**：接收時核對執行紀錄中的任務成員，拒收其他副本的提案。

真正多世界各有國家時，再加世界歸屬欄位；第一版不做。

### Q5：既有保存與補救流程可重用多少

- **去重**：`applyProposal` 已以提案 id（`state.receipts`）去重，重送同一提案不會重發效果。
- **提交**：外部提案須走與國策任務相同的提交流程：`writeState → proposedState → applyProposal → 換期排程`（`src/workflow.ts:463–490`）。只呼叫 `applyProposal` 會漏掉換期後續生成（`periods.push`）與排程紀錄（`state.schedules`）。建議把 run 流程中「取得結果」一步抽成可替換來源（模型請求或外部提案），其餘共用。
- **重試**：國策自己的請求在驗證失敗時會重試，外部提案則無法要求世界引擎重跑，失敗只能停在手動補救。`repairReply` 仍可先套用於外部提案。
- **手動更新與晚到提案的競爭**：既有「工作綁定來源樓層與 identity，swipe／編輯後舊工作不寫入」的機制可沿用。接收時另加規則：本樓已有手動更新結果則拒收提案。

### 分類總表

| 修改位置 | 內容 |
|---|---|
| 只改預設 | 世界任務加國策段（EJS 讀取或呼叫國策資料）；`extractInjectTags` 加入提案標籤；只讓指定世界的副本送出國策段；（若採 XML）關閉結構化輸出 |
| 改國策腳本 | 整合模式開關並停用自動局勢更新；提供本樓任務資料（window 函式或預存）；輪詢執行紀錄判斷世界成功；讀取提案、`repairReply`、走共用提交流程；終點時間對齊；swipe 與版本核對；介面狀態（待接收／失敗原因／成功） |
| 必須改工作流助手原始碼 | 只有一種情況：要在結構化 JSON 模式下可靠攜帶提案 |

### 與本文前述假設的差異（供使用者決定）

1. **接收欄位不需工作流助手新增功能**：現成的標籤抽取（`post_process_tags` 與執行紀錄 `extractedTags`）即可擔任「獨立接收欄位」，前提是世界任務走 XML。需決定：關閉結構化輸出（只改預設，解析失敗率待實測），或修改工作流助手原始碼（第三方專案，需自行維護分支或向作者提出）。
2. **完成標記不需新增**：執行紀錄已足以辨識成功、失敗與未到期；第 7 節 Q2 預期的「最小完成標記」可省略。
3. **國策資料提供方式**：第 5 節傾向預存欄位；Claude 建議渲染當下現算。若仍採預存，必須放寬 `until` 的精確比對。
4. **推進節奏**：整合模式下國策跟隨世界任務每週推進一次。長時間跳躍時，世界任務只執行一次並涵蓋整段區間（例如 72 天）。這與第 5 節「未到排程時間不另啟動自動國策推演」一致，但需在介面上讓使用者知道國策尚未追上本樓時間。

### 尚未驗證

- EJS 能否呼叫國策腳本掛在 window 的函式。
- 關閉結構化輸出後，世界任務在使用者常用模型上的解析成功率。
- 合併提示詞後的 token 量與推演品質。
- `世界状态摘要` 在純 JSON 輸出時是否確實停止更新（需在真實樓層比對）。

### 10.3 交付範圍：共同推演、人工接收國策

不再承諾「可靠自動同步」。第一版交付：

- 世界任務在同一次模型推演中產生世界更新與國策提案。
- 國策提案經國策規則驗證後，由**使用者確認接收**。
- 接收失敗或沒有提案時，使用國策自己的「局勢更新」手動補救。
- 國策自身的自動局勢更新照自身排程運作；本樓已有有效登記時讓位給世界提案（10.5「排程協調」）。
- 同一樓的工作流重跑可能覆寫本樓國策。程式提供偵測與提示，不承諾自動恢復。
- 提交前做忙碌檢查以降低寫入衝突，但沒有建立跨腳本的排他機制。

**第一版不提供自動接收。** 目前沒有可靠的完整成功訊號。日後若使用者明確要求，可加入使用者自行開啟的自動接收，其說明須寫成：「自動接收符合既有檢查的提案，仍無法確認世界完整寫入成功。」（見 10.13）

### 10.4 流程

```text
世界任務渲染提示詞
    ↓  EJS 呼叫國策資料函式：經協調入口檢查後，讀本樓國策與精確故事時間，登記 nonce
模型同一次回覆：<AddonJSONPatch> 世界更新＋<国策提案> 標籤
    ↓  工作流助手照原流程寫入世界；提案標籤存入 post_process_tags 與執行紀錄
國策腳本讀取提案，以 nonce 核對來源，依國策規則驗證
    ↓
顯示「待接收」：國策變更摘要＋世界執行證據（執行紀錄、世界現況、日誌問題）
    ↓  使用者確認
再次檢查來源、當前狀態與忙碌狀態 → 只保存國策 → 狀態顯示「國策已接收」
```

接收介面須分開呈現兩件事：「國策規則驗證通過」，以及「世界寫入沒有可供程式確認的完整成功結果」。不可把確認按鈕包裝成程式已驗證世界完整成功。

**以下情況直接拒收，確認按鈕不能略過：**

- 國策提案違反規則。
- nonce、聊天或分支不符。
- 輸入已被手動補救、國策自身更新或新請求取代。
- 使用者預覽後，相關資料又改變。
- 尚未接收就進入下一樓，或故事時間已改變：舊提案標記為過期，不改寫終點後套用。
- 世界更新有明確失敗，或忙碌檢查判定不可提交。

腳本重載後，無法恢復有效登記的提案一律不可接收，改走手動局勢更新。

### 10.5 國策腳本修改清單

|---|---|
| 整合模式 | 設定開關；啟用時清楚告知 10.7 的限制。國策自身的自動局勢更新保留，依「排程協調」讓位。 |
| 排程協調 | 國策控制器內單一協調入口，同時管理「提供外部提案資料」與「啟動國策自身局勢更新」。國策自身排程到期（沿用 `runScheduled` 的到期判定）時，在**不含 `await` 的同一段操作**中完成三件事：檢查本樓有無有效登記、取得本次執行權、使舊登記失效。有有效登記就讓位，本次不啟動，改等提案；沒有就照常執行，這**不表示**世界沒有執行。國策更新取得執行權後，即使失敗或取消，已失效的登記也不恢復。最終保存時仍核對登記與來源，作為第二層檢查。沒有有效登記時，先經「排程預測」決定是否短暫等待，再回到本入口決定執行權。 |

| 資料提供函式 | 掛在 `window.parent`，供 EJS `await` 呼叫（使用者 ST-Prompt-Template 的 `compile_workers`、`sandbox` 皆為關閉；整合模式需檢查這兩項並提示）。以參數接收樓號，讀 `getMvuData` 的國策、以 `storyDay` 規則解析精確時間、`workingState(state, full)`，附輸出格式、規則，以及**上次刊報以來實際保存的國策進展**（紀錄不足時標示不足，不從目前狀態倒推歷史；須確認不會被正文迷霧規則漏掉必要的執行結果）。未就緒（`Mvu.isDuringExtraAnalysis()`、缺 `stat_data` 等）或國策自身更新進行中時，回傳「國策資料暫不可提供」，讓模型本輪不提案。非同步準備完成、正式登記前，須再次檢查國策是否已開始更新、來源是否仍有效。 |
| 請求登記 | 只在真正的任務資料準備時登記 `{nonce, chatId, messageId, swipeId, 各國 cursor, now, 程式可比較的相關狀態}`。相關狀態須是可比對的結構化資料，不是自然語言摘要，也不能只靠會倒退的 revision。nonce 寫入給模型的資料，要求提案原樣帶回。同一樓產生新登記即作廢舊登記；提示詞預覽、重複渲染與快取命中不得誤作廢或誤登記。登記保存在腳本記憶體；重載後找不到登記即不可接收。有效登記只證明世界任務已取得國策輸入，不證明模型請求已送出；沒有結果的登記顯示「等待提案／可手動補救」，不顯示成「正在生成」。 |

| 介面 | 待接收／已接收／拒收原因／未就緒／等待提案／需手動補救／世界局勢落後天數。 |

### 10.6 預設修改清單

- 整合版世界任務**維持結構化 JSON 輸出**（`structuredOutputMode: addon_json_patch`，使用者 2026-10-04 決定）。提案以 `<国策提案>{"nonce":"…","proposal":{…}}</国策提案>` 寫在 `analysis` 字串內，與 `<世界状态摘要>` 相同；提示詞須說明 JSON 字串內的引號轉義。若日後實測提案常因轉義損壞，可改為 `structuredOutputMode: off`；提示詞已把提案放在思考內容中，兩種模式共用同一份文字。
- `extractInjectTags` 加入提案標籤；`finalInjectTemplate` 維持不變。JSON 模式下提案位於 `analysis`，會隨 `{{UpdateVariable}}` 進入本樓正文的 `<工作流变量更新>` 區塊（世界狀態摘要現在也是如此）；使用者的「[不发送]」正則（promptOnly）會在送出提示詞時移除整個區塊，所以提案不會送給正文模型，只在美化元件中顯示，並增加聊天檔大小。工作流助手只取最後一個同名標籤，提示詞因此要求 analysis 只在 Step10 末尾寫一次完整標籤。
- 新增國策段：以 `{{replica:val}}` 判斷，只對「阿斯塔利亚」送出；以 EJS `await` 呼叫資料函式；資料暫不可提供時不要求提案；說明提案格式與 nonce 回傳規則。
- 國策局勢更新的世界局勢段加入 10.5「每日更新提示詞」的規則。
- 另存整合版預設，保留原預設。

### 10.7 必須告知使用者的限制

- **同樓重跑可能遺失已接收的國策成果，以及接收後的手動修改。** 工作流重跑時以 `Mvu.replaceMvuData` 整包還原 baseline，而國策就在這個信封內。程式只能偵測並提示，不能防止或自動恢復。此限制須在啟用整合時明白告知，不能只寫在技術文件裡。
- 世界寫入是否完整成功，程式無法確認，只能由使用者審閱證據後接收。
- 讓位設計只保證：國策端不讓自身局勢更新與同一份有效外部提案同時取得套用資格；舊提案不因國策自身更新失敗而重新取得資格。它**不保證**第三方之後不覆寫已保存的國策（MVU 整包寫回、同樓重跑還原仍可能發生）。
- 國策自身更新與世界提案搶在同一樓時，可能失去該樓的共同推演，改由國策自身更新推進。
- 長時間跳躍時，世界任務一次涵蓋整段區間。
- 工作流助手在執行紀錄保存後，仍會整包寫入本樓訊息 data 兩次。使用者看完預覽才手動接收，實務上會晚於這兩次寫入，但不保證；若接收後被覆寫，介面會提示並允許重新接收。

### 10.8 另列：獨立模式的既有缺陷

與整合無關、現在已存在的問題，另行追蹤，不納入第一版：

- 國策自己的局勢更新若在工作流 MVU baseline 擷取之後提交，使用者重跑工作流會無聲遺失這次更新。
- 工作流 `applyMvuInjectPatch` 以「取得 → `await parseMessage` → 整包寫回」更新 MVU。國策若在這段期間提交，會被舊信封覆蓋；國策自己的 `VARIABLE_UPDATE_ENDED` 處理器也會把舊的 `国策` 複製進新資料。

### 10.9 若未來解除「不改第三方」限制

以下修改可提升保證，僅供參考，目前不做：

1. Addon 套用回傳完整結果（新增 API、保留舊 API 型別），區分合法無變更、解析失敗、未執行、部分失敗、寫入例外，並掛回來源任務與本輪識別。
2. baseline 還原與 MVU 寫回只合併已確認由 MVU 管理的欄位，保留其他命名空間；非同步解析後、寫入前再檢查取消與目標分支。
3. 結構化 JSON 模式保留額外欄位。

### 10.10 驗證案例

| 類別 | 案例與預期 |
|---|---|
| 提案接收 | 合法提案經確認後只保存一次；違反國策規則的提案直接拒收；同一提案重送或同時排入兩次，效果、排程紀錄與換期後續都只處理一次。 |
| 來源核對 | nonce、聊天、分支不符一律拒收；在模型請求、MVU 解析或保存前切換 swipe，舊提案不被接收；其他世界副本的提案被拒收。 |
| 精確時間 | 同一天不同時分的提案被拒收；正確的目標時間通過。 |
| 過期 | 尚未接收就進入下一樓或故事時間改變，舊提案標記過期，不改寫終點後套用。 |
| 預覽後變動 | 預覽後相關資料改變，確認時拒收並說明原因。 |
| 手動補救 | 開始補救即使舊提案失效；補救成功或失敗後，晚到提案都不復活。 |
| 世界重跑 | 已接收後重跑，偵測到國策回退並顯示提示；新提案與現況不相容時提示補救，不強制覆寫。 |
| 忙碌檢查 | MVU 解析期間不提交；狀態未知時不提交並顯示原因。 |
| 未就緒 | MVU 額外解析中或缺 `stat_data` 時，資料函式回傳暫不可提供，本輪不提案。 |
| 登記 | 提示詞預覽、重複渲染與快取命中不誤作廢、不誤登記。 |
| 重載 | 腳本重載後找不到有效登記，提案不可接收並給出原因。 |
| 環境 | `compile_workers` 或 `sandbox` 開啟時，整合模式提示無法使用。 |
| 預設 | 整合版維持 JSON 模式時，世界任務仍能正常寫入世界，並從 `analysis` 抽出 `世界状态摘要` 與提案標籤；提案內引號未轉義時，容錯解析仍能取回；提案不會送給正文模型（「[不发送]」正則移除 `<工作流变量更新>`）；analysis 中出現多個標籤時，取到的是 Step10 的最後一個。 |
| 排程協調 | 1. 世界先登記 → 國策自動更新讓位。2. 國策先開始 → 資料函式回報暫不可提供。3. 世界正在非同步準備資料、國策先取得執行權 → 世界不得再登記舊資料。4. 國策更新失敗或取消 → 舊 nonce 仍失效。5. 國策提交後出現新的世界請求 → 讀取新狀態並建立新登記。6. 已登記但世界沒有產生提案 → 不自行切回另一條自動更新；手動補救可正常解除等待。7. 國策自身排程未到期 → 不因沒有 nonce 就啟動。 |
| 排程預測：設定來源 | 聊天覆寫、停用任務、不同副本、成員不存在或定位不唯一；不得讀到其他世界的排程。 |
| 排程預測：到期邊界 | 差一分鐘、恰好到期、超過間隔、首次執行、聊天鍵不符、時間回退。 |
| 排程預測：日曆差異 | 跨 2 月、30 日月份及跨年時，預測使用 31／372 軸；國策時間與進度保持不變。 |
| 排程預測：支援範圍 | 不支援的模式、來源、格式，以及無法辨識的舊時間狀態，一律回傳未知。 |
| 排程預測：唯讀 | 預測前後，第三方設定與 `scheduleState` 不變。 |
| 預測等待 | 等待中出現 nonce → 不啟動國策自身更新。沒有任何工作流結果 → 達上限後重新走協調入口，同一來源不反覆等待。舊輪紀錄晚到 → 最多提前結束等待，不影響提案驗證，不解除有效 nonce。等待結束與資料登記幾乎同時發生 → 仍由同步的協調入口決定執行權。等待中切換聊天、swipe、編輯正文或開始手動補救 → 舊計時器不得再啟動工作。工作流已更新 `scheduleState` 但結果尚未完成 → 即使預測未到期，有效 nonce 仍優先讓位。預測未到期、但工作流以 `bypassSchedule` 手動重跑 → 仍由 nonce 正常協調。 |

### 10.13 日後的自動接收

使用者詢問：實測確認幾乎都能完整寫入後，能否改為自動接收。結論：

- 可以由使用者自行開啟，但說明須寫成「自動接收符合既有檢查的提案，仍無法確認世界完整寫入成功」，不可寫成「實測確認幾乎都完整寫入，因此可以自動判定」。
- 殘餘風險不只寫入錯誤，還包括輪次歸屬、晚到結果與後續覆寫。
- 第一版只保存 10.5 的診斷紀錄，作為日後評估的依據；自動接收本身不屬於第一版。
